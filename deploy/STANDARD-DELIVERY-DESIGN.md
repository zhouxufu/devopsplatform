# 标准交付与自定义编排设计

版本：1.0；日期：2026-10-13；状态：待评审方案。

普通交付以需求、Bug、版本或所选变更为起点，系统生成交付草稿，用户核对范围、制品、目标环境和执行顺序后提交。自定义编排保留为可选能力，不再成为普通交付的前置条件。

适用对象为研发、测试、发布审核人员及平台管理员。本方案覆盖交付准备、步骤生成、预检、审批、执行与追溯，不重新设计构建引擎、资源中心或日志存储。除“现有能力”章节明确列出的行为外，以下均为拟改造的目标。

## 目标与范围

核心目标是减少重复配置，同时保持发布安全：不用为每个需求新建模板，不为多个 Bug 重复发布同一应用，不因补资源或构建制品丢失交付草稿。

本次包含标准交付、自定义编排复用、多应用交付、按环境解析资源、审批策略继承和连续编辑。独立变更无需强制纳入需求或版本。

不包含任意 Git 分支无冲突自动合并、根据需求标题证明制品代码覆盖、任意 SQL 执行、跨 SQL 和 Nacos 的分布式事务、自动回滚数据库与配置、完整 DAG 并行编排。代码准备需要明确操作并沿用已有校验，保存需求、版本或草稿均不推送代码、不构建、不执行变更。

## 现有能力与待改造能力

| 能力 | 当前代码行为 | 本次目标 |
| --- | --- | --- |
| 交付入口 | 可以从工作项或版本进入交付准备 | 保留来源，默认使用标准交付 |
| 编排选择 | 有效模板和环境是解析交付计划的前提；仅有一个可用模板时自动选中 | 标准交付不要求用户创建或选择模板 |
| 来源范围 | 支持固定服务、版本、需求或 Bug；汇总关联变更并去重 | 增加直接选择独立变更的来源 |
| 执行步骤 | 来自模板，可调整本次步骤，但必须保留模板强制审核节点 | 由服务端生成候选步骤，并继承不可绕过的环境审核策略 |
| 制品与资源 | 制品需核对；预检解析环境资源，并冻结目标与基线 | 标准和自定义交付共用这些校验与执行器 |
| 预检和执行 | 预检不执行；提交执行单使用预检凭证；审批与执行分开 | 保持边界，增加草稿失效与定位反馈 |

现有入口依据为 OrchestrationView.vue 的 startDelivery、chooseTemplate，以及 delivery.go 的 ResolveDelivery、预检与执行单提交接口。本次不把“有发起交付按钮”表述为“无模板标准交付已实现”。

## 产品模型

| 对象 | 职责 |
| --- | --- |
| 工作项 | 说明交付目的，来源可为外部平台或自定义需求 |
| 变更 | 描述代码、SQL、Nacos、Redis、数据同步或人工操作，不直接绑定执行环境 |
| 发布版本 | 组织一组工作项和变更；不是执行计划，也不保证已经上线 |
| 交付草稿 | 保存本次来源、选择范围、环境、制品和步骤，可反复调整 |
| 交付策略 | 标准交付的生成规则及按环境配置的强制审核要求 |
| 编排模板 | 可复用的自定义流程，可按固定服务或动态来源展开 |
| 执行单 | 已提交的不可变计划、审核记录、执行状态和结果 |
| 执行台账 | 判断具体变更在具体目标上的执行证据，防止重复执行或不确定结果被重跑 |

关系为“工作项关联多个变更，版本组织范围，交付草稿选择本次范围，执行单冻结本次计划”。同一个变更可关联多个 Bug，同一个工作项可多次交付到不同环境。

工作项关闭状态、版本就绪状态和某环境的交付成功状态分开记录。只交付了工作项的一部分变更时，展示“部分交付”，不能因此把整个工作项标记为已上线。

## 页面与操作路径

统一采用“范围与环境 → 制品与步骤 → 预检提交”三步准备，提交后进入同一工作区的执行单详情。执行单详情包含审核、执行进度和结果，不再追加一串长弹窗。

从工作项进入时自动带入该工作项；从版本进入时带入版本；从变更列表进入时带入明确选择的记录；从编排列表进入时沿用所选模板。普通入口默认“标准交付”，高级入口可以选“自定义编排”。

### 范围与环境

展示交付来源、目标环境、发布原因和范围摘要。工作项及版本选择使用可搜索、可批量选择的宽弹窗；确认仅修改当前草稿，取消保留原选择。

按变更展示就绪、待补齐、已在该环境执行及需要核对等状态。未就绪内容可以查看和只读预检，但正式提交前必须补齐并就绪；不能自动把未完成变更标记就绪。用户可以明确排除本次不交付的内容，排除结果进入执行单快照。

来源默认值来自当前入口。目标环境可沿用当前工作区，但不存在或未绑定时明确提示，不悄悄切换其他环境。全局应用选择不能隐式改写多应用交付范围。

### 制品与步骤

上部显示每个待发布应用及唯一制品选择，下部显示系统生成的候选步骤。每个应用可以选择已有制品，或在当前交付上下文中进入代码准备和构建，完成后返回同一步，不自动改选“最新制品”。

只涉及 SQL 或配置的交付不要求选择应用制品；只有代码或制品发布意图才生成应用发布节点。多个 Bug 涉及同一应用时，选择一份覆盖本次范围的制品，并只生成一个发布节点。

步骤支持拖动排序和键盘上移下移。删除必须审核节点被禁止；不交付某项业务变更应回到范围选择显式排除，不能通过删步骤绕开已经确认的范围。

默认收起高级设置，提供“使用自定义编排”和“保存为模板”。调整本次顺序不改写原模板；仅明确选择保存才创建可复用模板。

### 预检提交

显示来源、选中变更、应用制品、实际资源目标、步骤顺序、审批流程、风险和阻断项。预检状态区分待检查、检查中、通过、有警告、被阻断和已失效。

阻断项自动定位对应步骤或字段，以可关闭 Toast 提示具体原因；不增加常驻大横条。成功状态和持续阻断原因仍保留在对应对象的状态中，不能只依赖短暂提示。

主按钮为“提交执行单，不立即执行”。提交后冻结快照并进入执行单；需要审批则等待审批，否则等待发起人手动开始。

## 步骤生成规则

生成顺序是“解析明确选择的范围 → 按变更编号去重 → 校验就绪情况 → 生成候选节点 → 合并环境强制审核 → 用户核对顺序 → 服务端预检”。生成草稿不进行远程写入。

| 内容类型 | 生成规则 | 必须核对 |
| --- | --- | --- |
| 代码和制品 | 按应用归并发布节点，绑定一份不可变制品 | 分支、提交、制品摘要和本次代码范围的覆盖证据 |
| SQL | 初始按应用和逻辑数据库资源分组，预检后按实际连接及事务边界拆分 | DDL 与 DML 分开；普通 SQL 同表多条 DML 的现有限制不得绕过 |
| Nacos | 按应用、逻辑资源和配置文档生成候选节点 | 环境绑定优先的 Data ID、Group、命名空间和基线；同文档多项修改需要明确合并或解决冲突 |
| 数据同步 | 仅引用已选择、已冻结的差异草稿，使用现有 SQL 执行器 | 未执行的对比任务本身不等于可发布变更；生产执行遵守变更审核 |
| Redis | 按逻辑资源生成明确命令节点 | 精确 Key、前缀、命令风险和执行台账；不做 Redis 数据同步 |
| 人工操作 | 生成有名称、说明和确认人的人工卡点 | 确认记录和实际完成条件 |
| 审核 | 根据环境策略及模板强制规则加入 | 指定人员、分阶段顺序、或签或会签，不允许客户端删减 |

同一资源别名在不同应用下不是同一个资源；同一应用的不同别名也不能因为名称相近而合并。不同数据库连接、环境、命名空间和配置文档不能误合并。

系统不能仅根据“SQL、配置、代码”三个类型判断真实业务依赖。示例顺序可以是 SQL → Nacos → 发布，但跨类型组合首次提交时必须明确核对；存在声明依赖时禁止违反依赖排序，无依赖依据时不得宣称顺序已经被自动证明安全。

已执行的变更只有在台账和实际目标校验一致时才能标记跳过。不确定结果、目标改变或内容改变必须阻断并核对，不能仅根据变更状态判断无需执行。

## 资源与制品核对

变更保留逻辑资源别名，执行环境在交付准备阶段选择。预检将“应用＋环境＋别名”解析为实际连接，展示可读目标但不暴露凭据。

SQL 展示连接、数据库、语句、结构校验结果、预计影响行数及上限。显式库名与环境绑定数据库不一致时阻断，不能自动删除用户意图后操作另一库。

Nacos 展示实际连接、命名空间、Data ID、Group、所选配置项差异及前后摘要。目标优先使用环境绑定，未指定时沿用变更默认值；最终目标缺失时定位资源绑定。重复配置项或同一父子路径冲突定位到具体配置项。

制品选择展示应用、分支、提交、构建编号、摘要、类型和产生时间。同一应用只保留一个制品选择，不以不同 Bug 分别部署。同一应用存在多个来源分支时，必须先形成一份覆盖本次范围的制品；当前无法自动验证的覆盖关系应标注“需人工确认”，不能伪装成系统验证通过。

切换来源、环境、选中变更、步骤顺序、制品或目标资源后，旧预检立即失效。可保留仍兼容的输入，但提交必须重新取得有效预检凭证。

## 审批与执行约束

系统角色仍为管理员与成员，不新增开发负责人、测试负责人等系统角色。这些名称属于审批阶段。

环境可以配置开发负责人 → 测试审批 → 项目管理审批三个阶段，也可以按实际需要配置阶段数量。每阶段独立指定人员并选择或签或会签。当前阶段通过后下一阶段才可审核；发起人不得自审，任一阶段拒绝则退回。

标准交付继承环境策略；自定义编排额外保留模板强制卡点，合并时不能削弱任一强制要求。生产无有效审批人、审批人全部不可用或仅有发起人时，阻断提交；成员同步不自动授予发布审核资格。

对 SQL、Nacos、Redis 等写操作继续沿用服务端执行限制，不能因为选择标准交付而免审。没有审核要求的环境也必须预检、提交快照并明确开始执行。

审批通过只解锁执行资格，不启动远程操作。修改执行内容需要新修订或新执行单并重新审核，旧意见保留为历史记录，不移植为新快照的同意。

应用发布沿用环境配置的金丝雀或分批策略。金丝雀指少量实例先发布并观察，不等同于流量百分比分配。需要人工继续时，观察条件满足后才能明确继续后续批次。

失败或中断后保留逐节点、逐目标台账并停止后续步骤。SQL、Nacos、Redis 和多个应用不是一个统一事务，不提供“一键整体自动回滚”的错误承诺。应用按既有策略恢复；数据库和配置需要单独的恢复计划或已审核的补偿变更。

## 草稿连续性与异常反馈

| 场景 | 行为 |
| --- | --- |
| 补应用资源或配置环境 | 在辅助面板中处理，关闭后返回原步骤，保留其他输入并重新解析目标 |
| 进入构建 | 保留来源、选中变更、环境和步骤；返回同一制品行，只提示新增候选，不自动选中 |
| 改变交付来源或范围 | 提示哪些选择将失效；明确确认后更新范围，不覆盖仍兼容的制品和自定义顺序 |
| 切换环境 | 保留交付意图，重新解析目标、审批和发布策略；清除执行许可及旧预检 |
| 从标准切到自定义 | 保留范围、环境、制品；展示模板步骤与当前步骤差异，确认后替换步骤 |
| 保存为模板失败 | 保留本次交付草稿，允许重试或继续，不丢失本次修改 |
| 字段校验失败 | 可关闭 Toast，自动切到出错类型、滚动并聚焦字段，修正后取消高亮 |
| 网络或权限错误 | 可关闭通知并提供重试；不跳到无关字段，不清空草稿 |
| 多人修改来源或目标 | 预检失效，保留输入并要求重新核对，不静默覆盖 |
| 关闭当前工作区 | 有未保存内容时提示；确认后遵守明确的草稿保存或丢弃选择 |

第一版至少保证同一工作区内的连续编辑与返回。页面刷新、浏览器退出后的恢复如未实现，不承诺自动找回，并提供明确提醒；服务端草稿恢复可作为后续增强。已提交执行单独立持久化，不受页面关闭影响。

## 技术设计与接口

### 服务端为计划生成的权威来源

增加统一策略解析入口，根据交付方式选择系统标准策略或已保存模板，再调用既有范围解析、预检和执行器。不得简单删除当前“有效模板必填”校验，让任意客户端节点绕过强制审批。

标准交付可使用不出现在用户模板列表中的虚拟策略对象，或一个受管理的内置策略；第一版建议采用服务端虚拟策略。该策略固定生成版本，环境策略有独立版本与摘要，二者进入执行快照。普通交付不为每个 Bug 创建一条模板记录。

自定义交付仍使用现有 template_id。同时传入标准交付与自定义模板参数时明确拒绝，不猜测用户意图。已有模板和历史执行单保持原解释，不批量重写。

### 拟新增请求与数据

| 字段或对象 | 用途 |
| --- | --- |
| strategy_kind | standard 或 custom，缺省请求按旧版模板语义处理 |
| source_type | 保留 fixed、version、work_items；新增 changes 表示明确选择独立变更 |
| selected_change_ids | 本次实际交付的变更范围，与排除项、来源摘要一起冻结 |
| strategy_version | 标准生成规则的版本 |
| policy_snapshot 和 policy_digest | 审批、环境保护和其他强制策略的不可变记录 |
| scope_digest | 来源和选中变更的摘要 |
| nodes 和 artifacts | 用户核对的步骤及每应用唯一制品；服务端重新验证 |
| preflight_token | 绑定操作者与本次完整计划的预检凭证 |

准备草稿可保留前端状态；执行单在现有 JSON 计划中补充策略快照。若增加持久化草稿或策略配置表，需要同时提供 SQLite 和 MySQL 迁移，而不是只支持某一后端。

### 接口调整建议

| 接口 | 目标 |
| --- | --- |
| POST /api/delivery/draft-plan | 新增，只读解析来源和生成候选节点，返回节点与来源变更映射、待补齐项和策略摘要 |
| POST /api/delivery/preview | 扩展支持 standard 和 custom，解析资源并签发预检凭证；不执行写操作 |
| POST /api/delivery/runs | 扩展支持标准计划；重新核对范围、策略、制品与预检凭证，幂等创建执行单 |
| GET /api/delivery/runs/{id} | 继续返回冻结计划、审核过程、节点状态与实际执行证据 |
| POST /api/delivery/templates | 保留；只在用户主动保存模板时调用 |

节点 ID 使用稳定的类型与逻辑分组标识。用户调整顺序后重新生成范围时，通过节点映射保留兼容编辑，不根据数组下标匹配或把新节点误当成旧节点。

预检凭证应覆盖操作者、来源及变更摘要、目标环境、策略版本、步骤、制品摘要、资源身份和预检有效期。过期、来源改变或策略改变后必须重新预检。重复点击提交不能生成多个执行单；网络结果不确定时先查询已有提交结果再决定是否重试。

### 状态与权限

草稿过程为 editing → preflighting → preflight_passed 或 blocked；相关输入改变后回到 editing。

提交后沿用现有执行状态：需要审核则 pending_approval；通过后 approved；明确开始后 running；遇到审核或批次卡点进入等待状态；结束为 success、failed 或 canceled。审核卡点与发布批次等待需要分别展示，不能把任一等待状态误报为成功。

只读候选生成不授予执行权。创建执行单、保存模板、审核、开始执行和继续批次分别做服务端权限检查；隐藏按钮不能替代鉴权。

## 视觉与组件规范

复用现有 PageHeader、Element Plus 输入和日期组件、表格、Toast 及平台明暗主题令牌，不引入新的视觉体系。桌面标题、步骤导航及主要动作保持紧凑，不用大说明卡片挤占编辑空间。

桌面上下文表单使用两列，制品与变更列表使用表格；步骤编辑支持紧凑列表。常用操作突出，资源设置、模板保存和规则说明放入辅助入口。保留“预检不执行”“提交不立即执行”等安全语义，但只在相关操作旁说明，不反复堆横条。

字段与动作位于同一工具栏，底边对齐；长 SQL 或配置值换行或在受控编辑区内滚动。固定底栏在布局中独占空间，不能覆盖表单最后一项。

验收宽度为 1440、900、700、390 像素。窄屏表单改单列，表格可横向滚动，不允许整页横向溢出；底栏按钮可以自然换行。

每个远程动作有 loading、防重复点击和成功或失败反馈。错误有字段位置映射，不能仅用“第几项”让用户猜测。步骤排序提供键盘操作，控件有标签，聚焦可见；跳转尊重减少动画设置。

资产使用现有 SVG 图标和组件，不需要新增营销插图。

## 实现拆分与验收

### 第一批实现标准交付闭环

实现服务端标准策略、来源解析与步骤生成；移除普通入口的模板必选；保留候选步骤、预检、环境审批与明确开始执行；复用现有发布及变更执行器。优先支持工作项、版本和独立变更的简单顺序交付。

### 第二批完善连续性与复用

完善范围变化后的兼容编辑保留、代码准备与构建返回、保存为模板、标准与自定义切换、逐环境执行证据及失败恢复入口。持久化草稿恢复如纳入本批，单独验收刷新和退出场景。

### 验收清单

- [ ] 没有任何用户模板时，工作项、版本及所选独立变更仍能发起标准交付。
- [ ] 仅 SQL 或 Nacos 的交付不要求选择应用制品；无对应内容的节点不出现。
- [ ] 多个 Bug 关联同一应用，计划只含一个应用发布节点和一份制品。
- [ ] 同一变更多处关联只纳入一次；排除范围明确且进入执行快照。
- [ ] 未就绪变更、无资源绑定、无制品、代码覆盖未确认和预检阻断均定位到具体对象。
- [ ] 跨类型步骤顺序可以核对调整；违反明确依赖的排序无法提交。
- [ ] 不同数据库、命名空间或配置文档不误合并；SQL 现有安全边界不放宽。
- [ ] 三阶段审批支持或签和会签，不允许跳阶段、自审或删除强制审核。
- [ ] 批准不自动执行；标准交付不绕过写操作审核。
- [ ] 范围、环境、目标资源、制品或策略改变使旧预检失效。
- [ ] 重复提交不产生多份执行单；结果未知时不盲目重试远程操作。
- [ ] 补资源、构建、切换步骤后输入保留；模板保存失败不丢失交付草稿。
- [ ] 仅主动保存才新增模板；本次调整不改写原模板和历史执行单。
- [ ] 已执行变更依据台账和目标校验跳过；不确定结果不能重复执行。
- [ ] 分批和少量实例金丝雀沿用环境策略，等待继续及失败状态可区分。
- [ ] 明暗主题及四档宽度无遮挡、无整页溢出，字段和按钮对齐。
- [ ] 自动化测试使用临时存储与模拟外部服务，不操作用户业务数据库和生产资源。

产品评审需确认跨类型推荐顺序的默认规则、环境审核策略的配置入口，以及第一版是否包含服务端草稿恢复。这些选择不改变“普通交付不必先建模板、预检和审批不自动执行”的核心原则。
