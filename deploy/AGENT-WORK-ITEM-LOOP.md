# Agent 驱动的需求与 Bug 闭环

日期：2026-11-18。状态：核心任务服务、页面和 MCP 已实现于工作区，尚未部署。以下“当前实现”描述实际边界；后文保留目标契约，不代表全部外部适配和无人值守能力已交付，也不构成业务执行授权。

## 当前实现

- 入口：工作项详情的“开发与交付跟进”。需求与 Bug 使用同一面板，任务活动时隐藏重复的交付入口；原编辑器保留草稿和离开保护。内部准备／执行单可在原页展开。
- MCP：`create_work_loop` 走冻结预览与一次确认；`list_work_loops`、`get_work_loop`、`save_work_loop_changes`、`start_work_loop_delivery`、`advance_work_loop`、`control_work_loop` 使用同一任务服务。`get_task_context` 在权限具备时附带任务。新增分发 Skill `devops-work-loop` 1.0.0，未自动安装到个人目录。
- 授权冻结：工作项、应用、环境、环境代码策略、流程摘要、构建方案、回归修订、完整／部分范围、期限与轮次预算。每次派发重新校验用户、Key 权限、修订和策略，不影响独立写工具原有确认。
- 协调：先持久化派发意图，复用原准备、范围确认、代码任务、交付和回归执行器。只自动确认本人提交范围；其他人的审批与人工验证仍等待指定人员。未知结果只核对原操作。
- 回归完成门禁核对本轮交付、应用、环境、节点、报告时间、制品 ID／摘要及授权测试集修订。部分范围只追加备注；完整范围成功才更新为待验收，关闭仍由人员完成。
- 来源支持：平台自建需求、平台自建 Bug、已接入的禅道 Bug。禅道的解决方式、解决版本和接收人从原生选项选择；来源回写保留原操作身份，失败不重启交付。**外部需求原生状态转换尚未适配**，授权阶段即明确拒绝。
- 调度边界：页面打开时或 Agent 持续调用原任务时自动衔接阶段，无须人逐个点击；**尚无脱离已认证客户端的后台全阶段调度器**。客户端离线后已启动的执行继续，后续阶段等待接续。
- 自动执行范围目前为代码／制品及绑定回归。SQL、配置、数据同步和脚本仍走独立风险审核，不能把它们从完整范围漏掉后宣称整个工作项完成。授权扩大／过期后的增量续授权、首页统一任务投影及外部需求适配仍属后续工作。

实际验证和限制见 `UI-INTERACTION-ACCEPTANCE.md` 本轮记录；合成用例不是实际业务发布证明。

## 用户确认的默认行为

页面和 MCP 同等支持 Bug 与需求的完整闭环，不以安装 MCP 或使用 Agent 作为页面操作的前提。开发／测试环境自动交付，回归通过后自动更新来源状态并添加备注：Bug 标记为已解决，关闭仍由测试人员决定；需求按来源真实流程推进至开发完成／待验收对应状态，最终验收由指定人员决定。这里的“开发完成／待验收”是平台语义，不是预设的来源枚举。

后续继续修复 Bug 或完善同一需求，允许新增或修改变更。目标是同一平台任务内完成查询、开发／修复、登记、交付、回归与来源回写，不要求人员在不同页面之间推进节点或核对状态。Bug 与需求在本轮实现范围内同等验收，不能只支持 Bug 后宣布工作项闭环完成。

平台保存任务、策略、审计、执行与来源回执；外部 Agent 在自己的代码工作区修复和测试。首期不以平台托管 LLM、常驻编码进程为前提。Agent 离线时显示等待 Agent，后台已启动的既有交付仍按原协调器运行；不能假装编码正在自动进行。

## 现有能力与真正的缺口

已核对代码与客户端工具清单：

| 环节 | 已有能力 | 缺口 |
|---|---|---|
| 查询 Bug／需求 | list_work_items、get_work_item、get_task_context、图片读取 | 上下文缺少统一修复轮次、自动化授权与机器可判定的下一步 |
| 保存与补改 | report_changes、add_work_item_changes、maintain_change | 每次独立预览确认；不能在任务授权内自动保存、校验与就绪 |
| 交付准备与执行 | 环境代码策略、preview_delivery、create_delivery_run、confirm_delivery_scope、start_code_preparation、advance_delivery | MCP 的操作确认与模板中的范围／人工节点叠加，准备到执行还没有任务级自动协调 |
| 回归 | 平台 API 测试和工作流验证节点 | 没有统一要求当前修复版本、当前交付制品与报告一一对应的任务完成门禁 |
| 来源状态／评论 | 现有 Bug 的 get_work_item_action_options、change_work_item_state；来源原生操作与去重标记 | 补齐需求的原生状态转换／评论适配，并统一接入交付后的可恢复回写阶段；不能把 Bug 接口名称泛化当作需求已支持 |
| 状态展示 | 工作项、准备、构建、执行、测试、来源回写各自有记录 | 缺少任务总状态、当前处理主体、统一事件和跨阶段恢复入口 |

现有工具仍要求冻结预览后的明确确认。不能让 Skill 忽略它们的契约，也不能直接删除全局确认机制。新自动化入口必须在服务端验证任务授权，并复用底层权限、校验、预检与原执行器。

## 使用流程

1. 用户从页面或 MCP 选择 Bug／需求及开发／测试环境，创建跟进任务。可以交给已连接的 Agent 开发，也可以由人开发后在原任务登记变更并启动自动交付。展示允许的应用、仓库、公共目标分支、动作、回归要求、来源回写规则、期限与执行预算。一条明确任务指令可创建对应授权，不再对每个普通步骤要求同样的确认。
2. Agent 读取当前上下文和验收条件，在独立工作区修复，提交实际 Commit 与本地验证证据。代码写入、提交、推送仍受客户端和仓库权限限制；平台不能替代缺失的代码工作区权限。
3. Agent 在本轮任务内新增或更新本人未冻结变更。平台校验关联、内容和修订，原子保存并标记符合要求的项就绪。保存不执行 SQL／配置。
4. 平台按已授权环境策略冻结源 SHA、目标 SHA、变更修订、构建方案与流程。自动做范围校验、代码准备、构建、正式预检及开发／测试执行；每一步仍记录预览、授权依据及回执，但不重复弹确认。
5. 平台运行要求的回归并核对实际部署制品。不能只凭编译成功、Agent 自述或上次报告把 Bug 标为已解决或需求标为开发完成。未配置有效回归要求时明确阻塞，不默认通过。
6. 达到门禁后，平台通过对应工作项类型的来源原生接口回写状态，同一次原生操作尽量附上开发／修复说明、Commit、目标环境、执行单与测试报告链接。状态名称、解决方案、需求完成转换及必填字段来自来源能力查询与类型对应的映射，不硬编码来源枚举或套用 Bug 的 resolve/close 操作。
7. Bug 由测试人员决定是否关闭，需求由指定验收人员确认验收。失败则保持待处理状态或按来源允许的规则重新激活，继续同一工作项的下一轮开发／修复。

## 页面与 MCP 的同等操作能力

页面在工作项列表提供“开始跟进”，详情页提供同一任务工作台，包含当前状态、开发轮次、变更内容、自动交付、测试结果、来源状态与备注。默认只突出当前可做的操作；历史执行记录展开查看。

| 任务操作 | 页面入口 | MCP 行为 |
|---|---|---|
| 查询与发起 | 需求／Bug 列表、工作项详情，选择环境和任务范围 | 查询工作项并创建同一类型任务 |
| 任务授权 | 显示本任务范围及自动化策略，确认启动一次 | 生成同内容的任务授权预览并确认一次 |
| 开发方式 | 交给已连接 Agent，或由人开发后登记 Commit 与验证结果 | Agent 获取任务上下文并提交开发结果 |
| 维护变更 | 原任务内新增、编辑、补充变更，显示历史修订 | 使用相同修订校验维护同一份内容 |
| 交付与回归 | “启动自动交付”，阶段自动衔接，原页持续更新 | 推进并读取同一任务状态与事件 |
| 异常处理 | 原页显示阻塞原因、差异及唯一对应的处理入口 | 返回结构化原因、允许动作、原记录身份 |
| 暂停与恢复 | 暂停新步骤派发、恢复原任务；在途操作显示真实结果 | 操作相同协调器，不另起执行单 |
| 状态与备注 | 查看自动回写，按权限追加备注或处理验收 | 使用同一来源适配器与幂等回执 |
| 后续开发 | “继续开发／补充修复”，沿用工作项创建新轮次 | 续接同任务的新轮次，不覆盖已执行快照 |

页面直接使用登录会话和来源账号权限，不要求用户创建 MCP Key。页面与 MCP 共享服务端任务服务、授权、修订校验、协调器和回执；不能在前端另写一套自动执行链。页面发起、Agent 接续，或 Agent 发起、页面接手，都必须核对同一账号或明确的任务接管权限、当前修订及活动租约，防止双重执行。

“交给 Agent”必须有可用的连接／认领通道；尚无 Agent 接入时展示待认领状态和任务引用，也允许人员直接接手。页面点击不能被表述为已经启动本地 Codex 或已经完成开发。

## 授权与确认精简

任务授权不扩大账号权限。页面实际可执行范围为：当前账号权限 ∩ 来源账号权限（涉及来源读写时）∩ 环境自动化策略 ∩ 此任务授权；MCP 请求还必须与当前 Key 范围取交集。每步都重算，撤销、过期或策略变化后不再派发新动作。页面与 MCP 切换不授予新权限，也不重复要求确认仍有效的同一任务授权。

授权必须固定工作项、应用集合、环境、仓库及目标分支策略、允许动作、回归集合／规则、允许的来源回写、期限、最大修复轮次与执行预算。Agent 不得自行扩展授权范围、降低测试要求或修改自己的审批策略。

| 操作 | 默认处理 |
|---|---|
| 读取、分析、本地编码与测试 | 继续；遵守客户端自身权限 |
| 本人未冻结草稿新增／编辑、校验就绪、进度备注 | 任务授权内自动，保留修订和审计 |
| 同任务／应用／环境的源 Commit 更新 | 创建新轮次和新的冻结执行快照，自动重新预检；不复用旧测试证据 |
| 已批准的开发／测试代码合并、构建、部署和回归 | 原权限／策略／预检满足后自动推进 |
| 普通 SQL／配置变更 | 环境策略明确允许的类别才自动；结构风险、影响范围和资源白名单由服务端检查，不能仅相信 Agent 标为“低风险” |
| 删除数据、破坏性 DDL、权限变更、任意脚本或无法判定的写操作 | 默认暂停在一个具体差异审核点 |
| 新增应用、环境或目标分支；扩大资源范围 | 展示增量差异，仅对扩大的部分重新授权 |
| 他人的确认／人工验收、生产与受保护环境 | 保留原审批；不得用 Agent 代签或伪造人工通过 |
| 远端结果未知 | 查询原操作与回执；不自动重新提交 |

开发／测试自动化模板应删除重复的本人“点击继续”节点，改为明确的机器校验节点。仍有指定人员审批或人工验证的既有模板不能被自动化入口偷偷跳过，任务显示具体等待人员和原因。策略选择自动化模板属于管理员可见配置变更，不重写已冻结执行单。

## 后续开发、补修与不可变记录

一个工作项对应多轮开发／修复；每轮关联独立的变更修订、代码提交、准备单、执行单和回归记录。需求分阶段交付时，某轮成功不能直接代表整个需求完成；回写需求完成前须满足本次授权的验收条件及完整交付范围。

- 草稿未冻结：修改本人原记录，使用 expected_revision／digest，保留修改历史。
- 已就绪但未冻结：显式转入可编辑修订，修改后重新校验；不能默默修改别人的就绪内容。
- 已冻结／执行中／已执行：原快照不动。产生新修订或新增补充变更，记录 supersedes／补充关系；不靠复制全部旧变更再次执行 SQL。
- 已成功执行项不因补修而重放。补充迁移使用新的迁移身份与执行台账；失败或未知项仍走原记录核对。
- 需求和 Bug 都实现状态与备注回写，分别查询来源工作项类型的动作、权限、必填字段及转换约束。平台自建工作项同样支持类型对应的状态流转与活动记录。
- 自动化启动前检查目标来源是否支持此类型的回写，明确缺失权限或适配能力；不得等交付后才发现需求回写未实现。已授权任务运行期间来源不可用时，保留“已交付／来源待回写”及恢复入口，不冒称来源已完成，也不重复交付。

## 统一任务与恢复

任务主状态：待接手 → 开发／修复中 → 校验中 → 交付中 → 回归中 → 回写中 → 待验收 → 已完成。人员可以直接接手；Agent 认领时明确显示 Agent 及绑定账号。待验收阶段，Bug 展示“已解决 · 待测试关闭”，需求展示其来源实际的开发完成／待验收状态；来源终态必须经实际回读确认。
另外保留：阻塞、等待人工、等待 Agent、已取消。底层执行状态、来源状态与任务状态分别存储，页面同时展示真实事实。

任务页持续更新“现在到哪一步、谁在处理、下一步是什么”，展开才显示内部准备单／构建／发布记录。列表、首页、工作项和 MCP 读取同一个任务投影。按钮只针对当前阻塞；恢复不要求用户重新定位多个页面。

交付成功但来源回写失败时，状态为“已交付／回写待处理”，仅恢复来源回写，不重新合并、构建或发布。执行失败后，Agent 可在授权范围内分析、补修并发起下一轮；超过预算或发生结果未知时暂停。

## 实现边界与次序

1. 部署插件新增任务／轮次／授权／事件持久记录与原执行引用，SQLite／MySQL 同一语义。授权激活前只保存草稿；以账号、任务修订和期限校验，不将聊天文字或浏览器偏好当授权凭证。
2. 增加任务专用 MCP 能力：读取上下文与下一步、创建任务授权预览、查询／暂停任务、提交或更新本轮修复结果。名称待实现时注册；本文不宣称它们已暴露。既有独立写工具保持现有确认规则。
3. 新协调器只编排既有变更维护、代码准备、交付与测试执行器，不复制另一套 SQL／配置／发布引擎。派发先持久记录意图，使用原操作 ID、锁和回执查询；重启或断连不自动重放未知动作。
4. 关联服务端验证的回归证据与来源回写门禁；操作 ID 按任务／轮次／动作去重，重连后核对来源历史。汇总关键里程碑备注，不为每次轮询刷评论。
5. 同一工作项页提供完整任务操作，不局限于 Agent 进度查看；MCP 和页面使用同一任务服务与状态投影。补齐需求来源转换和平台自建需求／Bug 的状态映射；更新配套 Skill，使任务授权内操作与独立预览确认路径明确分开。

## 验收标准

- 纯代码 Bug：一次任务授权后，完整通过“读 Bug → Agent 修复 → 登记／就绪 → 公共分支准备 → 构建 → 开发／测试交付 → 回归 → 已解决＋备注”；中途无冗余人工继续按钮。
- 需求同等闭环：读取需求与验收条件 → 开发 → 登记／更新变更 → 自动交付 → 回归 → 来源开发完成／待验收状态＋备注；指定人员验收后才完成，不能复用 Bug 的解决／关闭接口代替需求转换。
- 页面 × MCP、Bug × 需求四条路径分别端到端验收。页面路径不配置 MCP Key也能完成人工开发后的登记、自动交付、回归与回写；既有来源账号权限仍按原规则校验。
- 页面发起后由 Agent 接续，Agent 发起后由页面接手，状态与当前轮次一致；有效授权不重复确认，修订冲突／活动租约不能导致重复执行。
- 平台自建与已接入来源的需求／Bug 分别验证。未支持类型必须在启动前明确报能力缺口；有缺口的来源不能算闭环验收通过。
- 失败修复：仍在同一 Bug，允许修改未冻结草稿或追加下一轮变更；已执行记录、SQL 台账、原审批和原制品不变。
- 同一个身份被重复请求、MCP 重连、协调器重启，不重复提交来源评论或业务执行；不确定结果只核对。
- 回归失败、过期报告、制品不匹配、没有测试证据时不能标为已解决。不能以修改断言迎合实际响应作为修复成功。
- 权限撤销、任务过期、扩大范围、生产环境或他人审批均正确阻塞，只展示真正需要处理的动作。
