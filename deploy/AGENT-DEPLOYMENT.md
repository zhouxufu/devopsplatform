# Agent 部署模块：整包、自动回滚和多机隔离验证（2026-11-10）

复用现有 Agent 二进制，默认关闭；日志队列、采集方式和普通 JAR 发布步骤保持原样。代码完成隔离验证后，按用户追加授权于 2026-11-10 更新了测试服 192.168.0.32 的平台及部署模块，并提供 amd64/arm64 新版 Agent 安装包；没有升级业务机器上的 Agent、启用其部署模块或执行真实业务构建/发布。

## 接入范围与操作

Agent 通道支持托管 Java JAR、Java 完整目录包，以及现有发布单的多主机、并发、灰度和批间确认。仍使用原有应用、环境、不可变制品和审批流程，不增加新的发布页面。受保护环境保留原审批和自动回滚要求，发起人不能审批自己的发布。

应用环境的“启动与健康检查”中，只有已登记、唯一匹配授权 Agent 的主机才出现可选执行通道；普通 JAR 无 Agent 时不显示该字段，不增加必填项。选择 SSH 保持原通道，选择 Agent 后按主机匹配，提交发布时冻结主机到安装身份的映射。旧单机 deployment_agent_id 配置仍可读取。重复安装身份或主机授权不匹配会在构建/发布预检阶段报错，不猜测、不静默转用其他 Agent。

手动 API 配置可使用 deploy_config.deployment_transport=agent；平台在发布快照中生成 deployment_agent_ids（主机名到 Agent 身份的 JSON 映射）及协议标记。审批后新增或替换登记记录不会改变该发布单的目标。每台机器的任务独立绑定同一个发布单、冻结制品及目标环境。

新任务使用协议 v2；旧 Agent 不支持 v2 时拒绝执行，不能忽略整包或回滚字段。新 Agent 可以继续核对已经落盘的 v1 普通任务。启用扩展能力前需在明确授权的主机升级 Agent；本轮没有做这一步。

## 整包

复用现有 java-bundle / ssh-java-bundle 格式及清单。平台先校验制品摘要、应用归属、主 JAR、字节码和环境构建契约；Agent 再验证压缩包和冻结清单，逐文件核对长度、模式与 SHA-256。拒绝路径穿越、链接、设备、重复条目、不支持的扩展属性、缺失文件、损坏 CRC、额外压缩流和尾随内容。

Agent 在独立暂存目录完成解包，按解压大小检查暂存盘和目标盘空间；复制到新版本目录、校验 JDK，并同步文件和目录后才停止旧版本。包内启停脚本只保留，不自动执行。新版本不覆盖旧目录；准备完成后删除下载和解包副本，保留正式版本及任务收据。

整包压缩载荷和解压内容上限各 16 GiB、最多 100000 个成员；普通 JAR 载荷上限仍为 4 GiB。实际可部署大小受本地剩余空间限制。不同文件系统会分别检查，旧版本保留空间不会被强行回收。

GIS 的工具、只读数据及脚本可随完整版本恢复。持续变化的业务数据应保留在包外，通过应用现有配置引用；本轮不自动移动数据、创建共享挂载或修改业务路径。旧版本在发布期间发生内容变化时拒绝自动恢复并待核对，不能用回滚覆盖业务写入。数据库、Nacos、其他机器及外部系统不属于此文件回滚的事务范围。

## 自动回滚

发布前，Agent 冻结本机上一托管版本的目录、文件内容摘要、启动器和运行变量。原版本不可核验时，先进入待核对，不停止它。回滚策略随审批快照固定。

只有明确证明新进程启动失败或已经退出时，才按已选策略处理。启动观察默认 120 秒；超出、HTTP 尚未就绪、Agent 断连或回执丢失均为 needs_review（待核对），保留进程与执行锁，不按耗时自动停止或回滚。配置了端口/健康 URL 才能验证相应就绪条件；没有条件不能推断业务功能就绪。

执行自动回滚前再次确认目录归属、执行锁、当前失败版本、进程退出以及原版本未改变；随后原子恢复旧版本链接、用旧启动器和旧运行变量启动，实际就绪后才报告 rolled-back。首次发布没有旧版本时明确报告失败，不虚构成功回滚。回滚本身确认失败为 rollback-failed；结果未知为待核对，不强杀、不循环重试。旧变量中的敏感值也在本地回执中脱敏。

回滚意图和阶段先持久保存。worker 在切换或启动中崩溃，恢复过程只核对原版本与实际进程，不重放可能已经执行的启动/停止。能验证旧版本就绪才完成回滚，无法确定则保留执行保护。它不是长期守护程序；发布成功以后应用再崩溃、主机断电后的自动拉起，不在此发布回滚机制内。

本轮补齐的是发布阶段自动回滚。现有手动整单回退的执行器仍属于原通道；Agent 不会通过该入口偷偷回退到 SSH。需要人工再次发布时使用经过审核的历史制品与明确运行配置另建发布单，不能把它等同于自动恢复旧配置。

## 多机与恢复

批次的全部部署记录、发布单关联及进度先在一个数据库事务内提交，之后才向 Agent 暴露任务。每台主机独立任务、独立回执；下发不等于执行成功。并发上限由持久任务数控制，数据库行锁也约束多个平台进程；每个 Agent 还受自身本地并发上限约束。

本批实际就绪后再进入下一批。待核对暂停后续新下发，但不停止已运行的任务。默认失败阈值为 0，局部失败后取消未下发主机，等待已领取任务报告，不连带回滚已经成功的机器。明确配置的失败容忍数继续生效；待核对不能计为失败来绕过等待，灰度首批失败仍阻止后续。

批间暂停和已确认的“继续”均持久保存。平台重启恢复任务及收据，未派发记录只恢复调度，已经领取的任务不重发为新任务。批次创建和恢复使用条件更新，陈旧控制进程不能把已结束发布重新打开或把其他进程已创建的批次标成失败。

本地回执先同步再发送；平台事务提交任务序号、摘要和结果后 ACK。ACK 丢失补发相同收据，重复、乱序、冲突或终态后的改写被拒绝。启动/回滚不确定时不自动重放。当前每 Agent 最多约 1000 个任务目录，每任务 4096 条回执，满额背压；不丢弃未确认数据。长期归档和大量历史任务的轮询成本尚未做资源基准。

## 独立授权与进程

资源中心 → 主机 → 更多 →「部署 Agent 接入」提供自动接入。选择允许部署的应用后，目录从应用现有环境绑定中解析；预览展示主机、环境、执行用户、应用、目录和回连地址，10 分钟有效。管理员确认后自动安装或升级当前平台提供的 Agent、保留已有采集设置及持久身份、生成并下发独立令牌、配置固定 worker 启动器并验证回连。普通 JAR 的环境配置、通道选择与发布步骤不因此自动改变；启用授权不执行应用发布。

允许部署的应用可选“全部应用（*）”，持久保存为 `services: ["*"]`，与指定应用互斥；表示当前主机、当前环境中已绑定的托管 Java 应用。应用发现、唯一 Agent 选择及发布校验使用同一匹配规则。`*` 不改变本地目录策略，预览仍从当前符合条件的绑定解析具体目录并冻结；新增目录在发布前提示重新接入以更新授权，Agent 继续独立校验目录和链接。

重新打开或重新接入会沿用已保存的应用范围（包括 `*`）、平台回连地址及执行用户／组。预览接口省略相应字段时也复用原计划，显式提交空应用数组仍拒绝。目录根据现有绑定重新解析；预览后绑定变化仍须新预览，确认、独立 worker 证明和令牌激活流程不变。预览单独保留旧凭据已生效的目录，新目录在确认及回连验证前不能用于发布，重复预览也不能使其提前生效。旧凭据持续有效到新回连验证通过；不会因选择 `*` 自动修改现有授权或接入真实主机。

已有 Agent 沿用 systemd 执行用户，新装默认 logagent，可在预览前明确选择已有执行用户和组。需要已确认 SSH 指纹及 root/免密 sudo 运维权限。安装过程不递归改变已有队列、应用目录或任务目录的属主；所选用户须有实际部署目录的读写权限，无法核验的旧安装身份或原执行 UID 变化会拒绝接管。需要先修复权限的主机不能把“提交安装”当成“已接入”。

部署凭据仅在待接入时加密保存于服务端，上传至私有目录并最终写入权限 0600 的 Agent 配置；页面、审计和接口结果不返回令牌。独立 worker 的固定启动器由 root 管理，只接受受限任务编号，命令、systemd 属性和 UID/GID 固定，不授予任意 systemd-run/sudo 命令。worker 自检只产生私有证明文件，不执行应用命令；以所选 UID 启动到独立 systemd cgroup 后，Agent 才用新凭据回连，平台核对冻结身份与目录范围并激活授权。验证通过后清除服务端待接入凭据，只保留活动令牌摘要。

预览不影响现有凭据。轮换期间，旧凭据持续有效到新回连通过；活动或待核对部署阻止变更接入和轮换。先持久保存操作意图再下发，重复确认仅查询原操作；SSH 断连、进程崩溃或未知结果保留 needs_review，不自动重放安装。平台重开后仍可接受原身份的迟到回连。页面会短时轮询只读状态，也可手动刷新。停用会撤销领取新部署任务的授权，保留采集、历史记录和已运行的应用；存在活动任务时拒绝停用。

新增管理入口为 GET /api/hosts/{name}/deployment、POST .../preview、POST .../confirm 和 POST .../disable；写入口均要求管理员，确认绑定预览发起人及 operation_id。独立凭据的 POST /api/deployment-agent/enrollment 仅接收冻结接入证明，不接受发布任务或自由命令；网关只开放这一精确的数据面路径。

管理员通过 POST /api/deployment-agents 登记 agent_id、资源中心 host、environment 及允许的 services；必须使用已有 Agent 的持久安装身份，而非展示名。部署专用 Key 不能复用日志 ingest token，平台只保存摘要，令牌仅显示一次。GET /api/deployment-agents?service=...&environment=... 返回无凭据的授权列表；DELETE /api/deployment-agents/{id} 禁用后保留未核对任务。禁用不是杀掉已领取任务的命令。

Agent 配置仍是独立可选段：

```yaml
deployment:
  enabled: true
  url: https://platform.example/api/plugins/deploy/api/deployment-agent
  token: '<部署专用令牌>'
  state_dir: /var/lib/logagent/deployment-tasks
  allowed_roots:
    - /srv/devops-apps
  max_parallel: 1
```

状态目录与日志队列分开。采集配置更新保留部署 YAML、独立凭据、属主和权限，拒绝改变已建立的执行 UID。实际执行使用同一 Agent 的独立 systemd worker，UID/GID 不提升，应用不继承日志 Agent 的 cgroup/内存限制，不随控制进程重启而停止；已验证兼容 systemd 219。安装环境仍需明确授予该用户创建相应任务服务的权限，不自动修改本机授权。

isolated-process 只允许 loopback broker 的隔离 fixture，本轮容器测试使用此模式验证流程；生产仍使用 systemd。任务不向应用继承平台登录、SSH 或日志上报凭据。

## 验证范围

证据位于 artifacts/agent-deployment-v2-20261110/ 与 UI-INTERACTION-ACCEPTANCE.md。包括 GIS 目录结构的合成整包、真实 JDK8 进程、新进程退出后的完整目录和旧变量恢复、回滚中 worker 崩溃、三独立文件系统容器的并发/暂停、Agent SIGKILL、ACK 丢失补报，以及平台数据库重开和并发恢复。

没有发布或编译真实业务项目，没有更新现有业务 Agent、接管业务进程或操作业务应用数据库。测试平台的 MySQL 初始化已验证三张部署表成功创建且为空；更新前后既有元数据未发生变化。真实 GIS 业务、Flink/通用脚本、Docker 业务制品、Windows、主机断电和真实 MySQL 上的新调度锁事务未做本轮联调；不能用隔离用例推断它们已经上线或长期资源占用已验收。
