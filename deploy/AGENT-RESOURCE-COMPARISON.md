# 自研 Agent 与 vlagent 同机隔离对比

验收日期：2026-11-05。官方 vlagent v1.53.0，macOS arm64。

## 结果与当前选择

单看本轮资源指标，**vlagent 明显更省**。但它在本轮配置下不满足现有 Java 多行、稳定事件身份及崩溃恢复条件，不能把它直接替换成平台 Agent 后宣称功能、持久性相同。当前保留现有采集路径；vlagent 是后续适配的候选，不是已经启用的新默认。

| 指标 | 自研 Agent | vlagent |
| --- | ---: | ---: |
| 稳态 CPU（单核百分比，两轮均值） | 11.20% | 1.56% |
| 每轮处理 35,000 条的累计 CPU | 3.99 秒 | 0.62 秒 |
| 采样峰值 RSS（两轮均值） | 34.87 MiB | 25.79 MiB |
| Agent 进程归属磁盘写入 | 236.56 MiB | 0.65 MiB |
| 断连并强杀 Agent 后恢复耗时 | 1.71 秒 | 2.56 秒 |
| 最终唯一源记录 / 输入 | 35,000 / 35,000 | 35,000 / 35,000 |
| 最终物理记录（两轮分别） | 35,000 / 35,000 | 60,000 / 60,000 |

这里 CPU 是实测进程 CPU 时间，不是机器整体利用率。vlagent 稳态 CPU 约少 86%，采样峰值 RSS 约少 26%。没有用这些数值推算生产 Linux 的绝对容量。

## 方法

- 四轮串行按自研、vlagent、vlagent、自研执行，避免两者互相抢资源；每轮使用新建临时目录、六个合成日志文件和独立 VictoriaLogs 进程。
- 每条源日志 1,024 字节，包含中文和部分随机内容。每轮稳态 20,000 条、1,000 条/秒，再突发 5,000 条；断连时继续写入 10,000 条，并在其中强杀、重启 Agent。
- 两者磁盘队列额度都为 512 MiB，GOMAXPROCS=2，Go 软内存限制 50 MiB。vlagent 使用单发送队列、1 MiB 块及 16 MiB 缓存预算。这是受控配置比较，不是双方默认配置比较。
- 自研路径用本机合成接收器执行原 ACK 协议与事件 ID 去重；vlagent 使用原生协议转发到真实 VictoriaLogs。按日志内原始 seq 计算唯一源记录，同时保留实际物理记录数。
- 资源来自 macOS proc_pid_rusage，100ms 采样；CPU Mach 时钟按本机 timebase 换算，并与 getrusage 校准。只统计 Agent 进程，不包含接收器和后端的成本。磁盘计数为进程归属物理 IO，缓存命中可能不产生物理读取。

## 必须一起看待的语义差异

**磁盘写入不能按同等持久性直接排名。** 自研 Agent 持续写 SQLite WAL 队列（synchronous=NORMAL，并非每批 FULL fsync）。本轮 vlagent 在短时断连中的小积压留在内存块，磁盘状态只有几十字节；额外探针实测 pending_inmemory_blocks=3、persistentqueue_blocks_written_total=0。因此其低写入包含持久化策略差异，不只是编码或压缩效率差异。

**崩溃后可能重读。** 源文件保留时两者都找回全部 35,000 个源序号；vlagent 的两轮物理结果都是 60,000 行，即多写 25,000 行。本轮原生文件采集字段没有自研的稳定事件 ID；不能通过“按正文哈希”强行去重，否则合法重复日志也会被合并。

后续核对确定了本轮重读的直接原因：v1.53.0 的 checkpoints_db.go 每一分钟保存一次读取进度，正常停止时也会保存。本轮第一次启动约三十多秒即执行 SIGKILL，尚未到首次定时保存；重启日志明确记录 no checkpoints file found / read log files from the beginning。强杀前已成功写入的 25,000 条保留在后端，重启后又从文件头采集了全部 35,000 条（包括后续新增），合计 60,000 物理行、35,000 个不同源序号。不能将这一短时强杀结果泛化为正常重启固定重复 25,000 条；较长运行或正常停止的行为需分别测试。[固定版本保存进度源码](https://github.com/VictoriaMetrics/VictoriaLogs/blob/v1.53.0/app/vlagent/tail/checkpoints_db.go)。

**多行需要适配。** 相同五个物理行（异常首行、三个堆栈续行、下一条 INFO），自研配置原有行首合并后为两条事件，vlagent 原生文件采集为五条事件。这里没有声称所有协议或所有版本都不能处理多行，只说明所测文件采集路径不等价。

**源文件被清理后的恢复边界不同。** 另一个临时目录探针在断连时写 2,000 条，等待八秒后核对自研 spool 已有 2,000 条、vlagent 文件采集指标已读入全部记录。强杀 Agent 后移除这些合成源文件，再从同一 Agent 状态目录启动：自研恢复 2,000 条，vlagent 恢复 0 条。这个额外故障场景只删除自身临时源文件，不能将它表述为普通断连必然丢失。

此外，官方有界队列达到上限会淘汰最旧数据，自研现有策略是背压；本轮没有填满 512 MiB，未将此项写成容量实测结果。官方依据：[vlagent 文档](https://docs.victoriametrics.com/victorialogs/vlagent/)。文件处理依据：[v1.53.0 processor.go](https://github.com/VictoriaMetrics/VictoriaLogs/blob/v1.53.0/app/vlagent/filecollector/processor.go)。

## 切换门槛

若采用 vlagent，需要先解决源事件身份与至少一次补发去重、Java 多行及级别/时间提取、应用/环境/路径字段映射，以及断连队列的持久化和满额策略，再接现有受鉴权入口。直接绕过平台写后端会缺少查询游标、告警去重依赖的字段。本次没有更改真实 Agent 配置或对业务主机执行替换。

## 证据与限制

原始数据、配置参数、逐阶段采样、日志及可复现脚本保存在私有 gitignored 目录 `artifacts/agent-vlagent-compare-20261105/`：`result.json`、`summary.json`、`compare.py`、各轮 samples.json，以及 `semantic-probes/result.json` 和强杀前指标。

## 自研 Agent 第一轮资源优化

用户明确允许少量重复，希望先降低自研 Agent 占用。本轮先消除热路径开销，保持已有磁盘恢复队列及协议，不引入第二个采集器，也不将“允许重复”理解为“允许清除断连积压”。

- 持久化由每 100ms / 100 条调整为每 500ms / 500 条，正文达到 1 MiB 也立即提交；单条大事件最多再超过这个正文阈值 256 KiB。JSON 元数据和编码转义另占空间。小队列装不下一整批时逐步缩小提交前缀，由独立发送端排空后继续，不丢弃尾部。
- 复用 gzip 编码器和两个发送缓冲区，消除每次上报重建压缩窗口的开销；释放已持久化批次中的正文引用。
- 活跃文件 mtime 查询合并到最多每 250ms 一次，保留 EOF 时的轮转和 copytruncate 检查；常见单行读取减少一次临时字节复制。
- 事件 ID 生成去掉通用格式化开销，保持原字节格式与 SHA-256 结果，避免升级导致身份变化。没有为此次优化移除 Java 多行、应用/环境/路径、机器监控或 ACK 校验。
- GC 从 30 调到 50，Go 软内存预算仍为 50 MiB。先前尝试 GC=100 的 CPU 更低，但峰值 RSS 约 42 MiB，因此没有采用。Go 软预算不等于进程 RSS 硬上限。

最终重新执行优化前、优化后、优化后、优化前四轮串行比较；输入、持久队列模式、接收器和强杀恢复过程均相同，不能混用上节不同轮次基线来计算收益。

| 指标（各两轮均值） | 优化前 | 优化后 |
| --- | ---: | ---: |
| 稳态 CPU，单核占比 | 10.23% | 7.61% |
| 每轮累计 CPU | 3.74 秒 | 2.75 秒 |
| 采样峰值 RSS | 34.96 MiB | 37.38 MiB |
| Agent 进程归属磁盘写入 | 235.95 MiB | 171.66 MiB |
| 断连恢复耗时 | 1.91 秒 | 1.71 秒 |
| 排空后队列文件分配空间 | 26.10 MiB | 27.10 MiB |
| 最终物理行 / 不同源序号 | 35,000 / 35,000 | 35,000 / 35,000 |

本轮稳态 CPU 降约 26%、磁盘写入降约 27%，峰值 RSS 增约 2.4 MiB；并未降低每项资源。批量提交使低流量情况下的入队定时等待上限由 100ms 增为 500ms，仍叠加文件追读、网络重试及服务端处理时间，不能宣传端到端 500ms SLA。队列仍为 SQLite WAL/NORMAL，没有新增断电持久性承诺。

入队之前突然退出的事件仍依赖源文件重读；该定时等待窗口变长，不能保证在尚未提交且源文件同时被清理时不丢失。已经提交的断连积压仍由原 spool 恢复，不主动丢弃。500ms 是定时批量提交目标，队列满、调度延迟等情况下不是硬上限。

最终证据在 `artifacts/agent-resource-opt-20261105/`：compare.py、四轮 result.json / samples.json、summary.json、agent-candidate。GC=100 的试验单独保存在 attempt-gc100，不计入最终指标。本轮没有替换本地实际 Agent 或业务主机上的 Agent。

额外通过 Go build overlay 给隔离二进制加 CPU profile（未给产品增加诊断端口或参数），在完整 35,000 条合成链路、无强杀的独立轮次中正常退出并关闭采样。42.77 秒采集得到 1.43 秒 CPU 样本；SQLite Xsqlite3_step 累计约 37%，SHA-256 block 约 0.7%。这些累计栈包含子调用，不能相加；本轮未采 vlagent CPU profile，不能用此比例精确拆分两者差距。独立 profile 轮次与全量回归并行，不计入上表资源排名。证据 cpu-top.txt、cpu-cumulative.txt、profile-run.json 及 .pprof。
