# Agent 分段顺序文件队列

2026-11-05：以分段文件替换 Agent 热路径中的 SQLite 队列。此次仅构建、隔离验收，没有更新业务机器、本地实际 Agent 或测试服。服务端日志正文仍由 VictoriaLogs 保存，服务端 state.db 的告警与有限投递队列不属于本次改动。

## 运行方式

保持原 `spool` 配置路径与 `spool_max_mb` 字段，配置界面和上报协议不变。假设原配置为 `/var/lib/logagent/agent-spool.db`，新运行文件为：

| 文件 | 用途 |
| --- | --- |
| `agent-spool.db.queue/segment-*.qlog` | 顺序追加的压缩批次，分段目标 16 MiB |
| `agent-spool.db.queue/checkpoint.json` | 带校验的 ACK 序号、末序号和源文件断点 |
| `agent-spool.db.queue/identity.json` | 原安装身份与历史名称，独立原子保存 |
| `agent-spool.db.queue/format.json` | 显式格式版本与旧库导入标记 |
| `agent-spool.db.queue/quarantine/tail-*.bin` | 重启时发现的不完整尾块原始证据（按内容摘要区分，重复损坏不覆盖旧证据） |
| `agent-spool.db.queue.lock` | 单写进程锁；只读身份检查不占该锁 |

每个批次用有界二进制字段编码完整事件和源断点，gzip BestSpeed 压缩。块头包含长度、记录数、起始序号、头 CRC 和载荷 CRC；单块原始/压缩长度上限均为 8 MiB，记录数上限 4,096。普通 Sender 仍按 500ms、500 条或约 1 MiB 正文批量入队。块数量、长度、字段边界和解压长度均检查后再读取/分配。

## 投递和恢复语义

1. 完整块写入并执行文件同步，新建分段还同步目录；成功后才允许外部 registry 推进。源文件暂未进入持久块的内容仍依赖原文件重读。
2. 发送时读取最早的未确认批次；服务端批次号和确认数量全部匹配后，才推进内存中的连续 ACK 前缀。保留原事件 ID、时间、应用/环境/主机/路径、级别、Trace 和 Java 多行正文。
3. ACK 与源断点合并保存，目标间隔 5 秒；正常关闭强制保存。检查点尚未保存时强杀，最近已确认块可能重发，载荷和事件 ID 保持原样。间隔不是实时硬上限。回收暂时失败时保留正确容量记账，后续强制检查点可重试清理。
4. 只有确认位置及相应源断点已成功写入检查点后，才删除整个已确认分段。检查点写失败不回收数据。保存源断点后，即使分段已回收、外部 registry 丢失，也能恢复文件世代和读取位置。
5. 完整坏块、头/载荷校验失败、缺失未确认分段、检查点损坏或未知格式会明确报错，保留原文件与有效后缀；不猜测偏移并跳过。仅最后一个分段的未完成尾块可先完整留证，再退回最后完整块重放。留证失败则不截断。

没有承诺物理 exactly-once、真实断电或介质损坏下零丢失。完整批次同步比原 WAL/NORMAL 每批不强制同步更积极，但仍需独立断电验收。保持有限内存和原 50 MiB Go 软预算；它不是进程 RSS 硬上限。

## 容量口径

`spool_max_mb` 限制压缩分段文件及已留存尾块证据的文件长度；文件系统分配粒度、目录/小元数据、旧库及未完成导入暂存目录另占空间。已 ACK 但尚不能整段回收的部分也占额度。满额时暂停追读，不删除旧积压换取新日志；小配额装不下一整批时先提交可容纳的前缀，由发送端排空后继续。

兼容字段 `spool_bytes` 仍表示未发送的未压缩编码大小（含元数据的估算），ACK 后减少；它与压缩磁盘占用不是同一个口径。实际磁盘资源对比使用状态目录文件的分配字节。

## 旧 SQLite 队列升级

- 必须先停止旧 Agent，避免老版本继续写库。正常 systemd restart 会先停止旧进程再启动新进程；手工启动前须自行确认旧实例已退出。
- 新目录不存在时，以只读 SQLite 事务快照导入待发送事件和原安装身份；在独立暂存目录完成所有块、检查点与格式文件的同步后，原子发布整个新目录。失败不发布半份队列，也不修改/删除原库。
- 新目录已存在时只使用分段队列，不再读取或双写旧库。旧 `agent-spool.db`、WAL/SHM 和外部 registry 保留；原库作为冻结备份仍占磁盘，不纳入新队列额度。已有积压超过新额度时先保留并补发，新的追读受背压。
- 导入中被强杀可能留下同目录下 `.agent-spool.db.queue.import-*` 暂存目录；它不是已激活队列。保留以便检查，不自动清除。重新启动会从未改动的旧库创建完整导入；升级需为暂存与旧备份留足空间。
- 不可直接用旧二进制降级：旧程序不会读取新队列，只会打开已冻结的 SQLite 文件。回退须先停止并处理分段积压、核对源断点和身份，不能把旧库当作当前队列。

## 同机资源对比

对照是上一轮已经优化过的 SQLite Agent，而不是更早的高占用版本。两者均为相同采集/500ms 批量/发送协议/50 MiB 软预算/512 MiB 磁盘额度；不同点是队列格式与同步/回收方式。旧版配额按未压缩待发送载荷计算，新版按压缩分段/证据文件长度计算；设置值相同不等于可缓冲相同条数，本轮没有触发 512 MiB 上限。新队列完整批次执行 Sync，旧队列为 SQLite WAL/NORMAL，并不宣称相同断电持久性。

四轮串行顺序：SQLite、分段、分段、SQLite。每轮六个合成文件，每行 1,024 字节；稳态 20,000 条、1,000 条/秒，再突发 5,000 条，断连期间写入 10,000 条并强杀、重启 Agent。总输入 35,000 条，约 34.18 MiB。新建独立 VictoriaLogs 后端和临时目录，不访问业务机器。

| 指标，各两轮均值 | 当前 SQLite 版 | 分段文件版 |
| --- | ---: | ---: |
| 稳态 CPU，单核占比 | 7.49% | 4.73% |
| 每轮累计 CPU | 2.82 秒 | 1.95 秒 |
| 采样峰值 RSS | 38.35 MiB | 29.34 MiB |
| Agent 进程归属磁盘写入 | 177.01 MiB | 4.04 MiB |
| 断连时状态目录分配空间 | 26.10 MiB | 3.05 MiB |
| 恢复补发等待 | 1.70 秒 | 1.50 秒 |
| 最终物理行 / 不同源序号 | 35,000 / 35,000 | 35,000 / 35,000 |

本轮稳态 CPU 约降 37%、峰值 RSS 约降 24%、进程归属磁盘写入约降 98%。恢复在本轮均为约 1–2 秒，样本量小，不作恢复速度承诺。排空后的即时目录快照分别为 27.60 / 3.05 MiB；取样在排空后短暂等待时，分段版仍可能保留尚未到检查点的已确认块，不等于长期空队列占用。

macOS arm64 共享开发机，100ms 采样进程 CPU/RSS/磁盘 IO；CPU Mach 时钟与 getrusage 校准。仅 Agent 进程，不包括合成接收器和后端；物理磁盘计数受文件缓存影响。接收器按事件 ID 去重，不能据物理行数宣称没有网络重试或物理 exactly-once。未做生产 Linux 运行、长时间满负载、真实断电/磁盘损坏和大规模满盘试验。

额外真实 Agent 验证：五物理行 Java 异常仍合为两条事件；断连时写入并核对 2,000 条已在有效分段块中，强杀 Agent 后删除自身临时源文件，恢复后 2,000 条完整补发，无逻辑遗漏。源文件在确认持久化前被删除的情形不在这个保证内。
